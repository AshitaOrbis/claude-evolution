## Novel Discoveries (8)

### 1. CwdChanged and FileChanged Hook Events (v2.1.83)

**Status**: NOVEL — not in registry
**Type**: technique
**Source**: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md#2183

New hook events for reactive environment management:
- `CwdChanged`: Fires when working directory changes (e.g., user `cd`s to different project)
- `FileChanged`: Fires when a watched file changes on disk

Primary use case: direnv-style automatic environment loading. When session CWD changes to a directory with a different `.envrc`, `CwdChanged` can fire a script to reload environment variables via `$CLAUDE_ENV_FILE`. Distinct from `PostToolUse(Bash)` which fires on ALL bash commands — these events fire on directory/file state changes specifically.

**Capability gap this fills**: Currently no way to reactively update environment variables mid-session without user intervention. Enables automatic credential rotation, direnv integration, and hot-reloading of project-specific config when navigating across projects.

**Registry status**: Hook events section needs two new entries.

### 2. CLAUDE_CODE_SUBPROCESS_ENV_SCRUB Security Feature (v2.1.83)

**Status**: NOVEL — not in registry
**Type**: technique
**Source**: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md#2183

`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` strips Anthropic API keys and cloud provider credentials (AWS, GCP, Azure) from the environment before passing to subprocess environments: Bash tool, hooks, and MCP stdio servers.

**When to use**: Any session where subprocesses or MCP servers should not have access to the invoking session's cloud credentials. Security-sensitive automation runs, CI/CD, untrusted MCP servers.

**Relationship to existing**: Complements Agent Spawn Restrictions (limits WHICH agents run) and `--bare` mode (reduces overhead). This is specifically about credential isolation in subprocess environments — a gap not covered by existing controls.

### 3. Agent initialPrompt Frontmatter Field (v2.1.83)

**Status**: NOVEL — not in registry
**Type**: technique
**Source**: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md#2183

Agents can declare `initialPrompt` in their frontmatter YAML. When the agent starts, this prompt is automatically submitted as the first turn — no orchestrator boilerplate needed to "kick off" an agent.

```yaml
---
name: my-agent
initialPrompt: "Begin by reading CLAUDE.md and summarizing the project state."
---
```

**Value**: Removes the pattern where orchestrators include a preamble like "Tell the agent to start by doing X" in every invocation. The agent self-starts. Reduces orchestrator prompt length and ensures consistent agent initialization.

**Relationship to existing**: Complements Agent Spawn Restrictions and Agent Memory frontmatter. The three frontmatter fields now form a cohesive agent configuration system: what tools it can use, what memory scope it has, and how it starts.

### 4. PreToolUse Hook Can Satisfy AskUserQuestion (v2.1.85)

**Status**: NOVEL — yesterday's report noted this was pending, pipeline is now empty
**Type**: technique
**Source**: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md#2185

PreToolUse hooks can now respond to `AskUserQuestion` tool calls by returning `updatedInput` with `permissionDecision: "allow"`. This enables fully headless automation of interactive sessions that previously required user input for questions.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow",
    "updatedInput": {
      "question": "Which approach do you prefer?",
      "selectedOption": "A"
    }
  }
}
```

**Capability gap**: Before this, `AskUserQuestion` calls in headless (`-p`) sessions would block indefinitely or fail. Now hooks can inject answers programmatically, enabling fully automated agentic pipelines without any interactive prompts breaking the flow.

**Score estimate**: 81.75/100 (from yesterday's analysis in the daily report, not yet filed as evaluation).

### 5. MCP headersHelper Server Context Env Vars (v2.1.85)

**Status**: NOVEL — not in registry
**Type**: technique
**Source**: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md#2185

Two new env vars available inside MCP `headersHelper` scripts:
- `CLAUDE_CODE_MCP_SERVER_NAME`: The name of the MCP server being connected to
- `CLAUDE_CODE_MCP_SERVER_URL`: The URL of the MCP server

**Value**: Previously, a `headersHelper` script had no way to know which server it was generating headers for, so you needed one script per server. Now a single helper script can serve multiple MCP servers by branching on the server name/URL — e.g., different API keys for different data providers, different auth schemes per domain.

**Relationship to existing**: Directly extends the `headersHelper` MCP configuration that's used for authenticated HTTP MCP servers. Not a new capability — an improvement to an existing one.

### 6. managed-settings.d Drop-in Policy Directory (v2.1.83)

**Status**: NOVEL — not in registry
**Type**: technique
**Source**: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md#2183

`managed-settings.d/` is a new drop-in directory alongside `managed-settings.json`. Policy fragments (individual `.json` files) placed here are merged alphabetically into the managed settings.

**Value for current setup**: Even for single-user setups, this enables:
1. Separate files for separate concerns (security rules, MCP allowlists, model settings)
2. Version control of individual policy fragments without merge conflicts
3. Per-project policy overlays that build on a base set
4. Tool-managed policy updates (scripts can write a file to `managed-settings.d/` without overwriting global policy)

**Relationship to existing**: Complements `managed-settings.json` (the single-file approach). The two coexist — drop-in files merge with the base file.

### 7. PostCompact Hook Event (Undocumented in Registry)

**Status**: NOVEL — in official docs but not in registry
**Type**: technique
**Source**: https://code.claude.com/docs/en/hooks

`PostCompact` hook fires after context compaction completes. Distinct from `PreCompact` (fires before, can influence what's preserved).

**Value**: `PreCompact` is already in the registry. `PostCompact` completes the compaction lifecycle — useful for:
- Notifying external systems that a compaction occurred
- Logging compaction events for debugging context issues
- Triggering re-injection of critical context after compaction (e.g., re-loading CLAUDE.md pointers)
- Coordinating with background agents that may be affected by parent context compaction

### 8. Elicitation and ElicitationResult Hook Events (Undocumented in Registry)

**Status**: NOVEL — in official docs but not in registry
**Type**: technique
**Source**: https://code.claude.com/docs/en/hooks

Two new hook events related to MCP server user input requests:
- `Elicitation`: Fires when an MCP server requests user input during a tool call
- `ElicitationResult`: Fires after a user responds to an MCP elicitation

**Value**: Enables hooks to intercept and programmatically respond to (or log) MCP server input requests. For automated pipelines, `Elicitation` could auto-respond to MCP servers that occasionally prompt for confirmation, preventing pipeline interruption. For audit trails, `ElicitationResult` captures what users actually said to MCP servers.

**Relationship to existing**: Extends the hook lifecycle to cover MCP-initiated interactions. Fills a gap where MCP servers that use elicitation could break automated workflows.
